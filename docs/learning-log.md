## 2026-10-11 · RAW files and decoding
A RAW file is not an image. It holds one brightness number per sensor pixel, where each pixel sits under a red, green or blue filter in a checkerboard (Bayer mosaic), plus metadata on how to interpret them. A **decoder** subtracts the sensor's black level, scales to the white level, **demosaics** (estimates the two missing colours per pixel from neighbours), applies white-balance multipliers, and converts the camera's colour primaries to a standard space using a **colour matrix**. The result is a linear RGB image.
**Why it mattered:** this is the only camera-specific step. After decoding, everything is camera-agnostic, which is why picturesq supports any LibRaw camera (ADR-0001).

## 2026-10-11 · D-Log LUTs don't apply to DNG
DJI's "conversion LUTs" turn D-Log *video* into normal-looking Rec.709. D-Log is a log curve plus a wide gamut that the camera bakes into video files. A DNG still is linear sensor data with no log encoding. Applying a D-Log LUT to it means feeding the LUT inputs it was never designed for, and the colours and contrast come out wrong. A LUT only gives correct results when the input is in exactly the colour space and transfer curve it was built for.
**Why it mattered:** we dropped the camera-LUT stage entirely (ADR-0002), and every user `.cube` file must declare its input space.

## 2026-10-11 · Linear vs display encoding
In **scene-linear** data, a value is proportional to light: double the light, double the number. Displays and JPEGs use a **non-linear encoding** (sRGB "gamma"), which spends more code values on shadows because human vision is more sensitive there. Maths that mimics physics (exposure, white balance, blending light) must happen in linear. Doing it on gamma-encoded values distorts contrast and colour, a classic mistake.
**Why it mattered:** the whole pipeline works in float32 linear and converts to sRGB only at export.

## 2026-10-11 · Display transforms (tone mapping)
A sunny scene can span 15+ stops; a screen shows about 6–8. A **display transform** compresses scene-linear values into the 0–1 display range: it decides how highlights roll off, how contrast feels, and how bright saturated colours fade toward white. Naive per-channel curves skew hues (skies turn cyan, sunsets yellow). AgX and OpenDRT are open designs that avoid this.
**Why it mattered:** AgX is our neutral base (ADR-0003); every look builds on it.

## 2026-10-11 · The memory maths of a 33 MP photo
7680 × 4320 ≈ 33 M pixels. As float32 RGB that's 33M × 3 × 4 bytes ≈ **400 MB per array**. A numpy expression like `a * b + c` allocates temporaries, so a naive chain can peak at 1–2 GB per image. On an 8 GB laptop, memory, not CPU, limits how many photos run in parallel. Per-pixel ops on a 1000 px proxy (~0.5 MP) are ~60× cheaper, which is why interactive previews always use proxies.
**Why it mattered:** proxy-first design, in-place ops, memory-capped worker pool, and memory budget tests (project plan §5).

## 2026-10-11 · Proxies
A **proxy** is a small (2048 px long edge), cached, **scene-linear** float16 copy of a photo; the term comes from video editing. It has ~14× fewer pixels than a 33 MP original, so operations take milliseconds. It's scene-linear rather than a JPEG thumbnail, so normalise and grade behave exactly as they will on the original: what you preview is what you export. Float16 halves storage versus float32 while still holding values above 1.0 (bright skies), which 8-bit can't. The cache key hashes the original, the decode config and the version, so a proxy is never stale. A **preview** is the display-ready render *of* a proxy.
**Why it mattered:** every interactive feature (contact sheets, the UI, normalise stats) uses proxies; only export touches originals. This is what makes an 8 GB, CPU-only laptop enough.

## 2026-10-12 · Inside a Pocket 4 DNG
A DNG is a TIFF holding several images: IFD0 has a 160×90 thumbnail plus all metadata, and sub-IFDs hold the **raw data** and a **720×1280 JPEG preview** (the camera's own rendering). Surveying ~350 Pocket 4 DNGs (`Model: OP-041`) showed: the raw is a **Bayer mosaic** (`R G / G B`), not a linear DNG, so demosaicing is ours to do; it's stored **uncompressed** in 16 bits (≈ 41 MB at 21 MP, 64 MB at 33 MP); **black level 0** (most cameras report a few hundred, so the camera likely subtracts it already) and **white level 62400**; two **colour matrices** (calibrated under tungsten and D65) that a renderer blends according to white balance; and `AsShotNeutral`, the camera's white balance, *recorded but not applied*. Three raw sizes appear: 7680×4320 (33 MP), 6144×3456 and 6144×3584 (21–22 MP, portrait). rawpy reported an all-zero `rgb_xyz_matrix` for these files.
**Why it mattered:** demosaic quality matters for this camera; the embedded preview is too small for a full-size in-camera baseline, so we shoot JPEG+DNG; and decode (#15) must check whether LibRaw really applies the DNG colour matrices before we trust its colours.

## 2026-10-12 · BaselineExposure: the camera underexposes on purpose
The Pocket 4 records the raw **2–4 stops darker** than the final image should look, so bright highlights don't clip: in ~350 photos, none had more than 1 % of pixels near white. The DNG tag `BaselineExposure` tells renderers how many stops to brighten (×2 per stop), and it **varies per photo** (from about +0.6 to +4 EV). The median raw pixel of a normal daylight photo sits at only ~2–6 % of white. So "underexposed" only means something *after* BaselineExposure is applied.
**Why it mattered:** decode must read BaselineExposure per file, or every render comes out ~3 stops dark; normalise measures exposure after applying it; and the AgX display transform has to roll off the highlights this headroom preserves instead of clipping them.

## 2026-10-12 · Bit depth and quantisation
*n* bits give 2ⁿ values: an 8-bit JPEG channel is a whole number from 0 to 255. Storing continuous light means rounding to the nearest step (**quantisation**). Steps are invisible until you stretch them: brighten a dim sky that spans 20 JPEG values by 2 stops and it still has only 20 values, now 4 apart, so you see **banding**. In a linear encoding each stop down gets half the remaining steps (8-bit linear: 128 steps in the top stop, 4 in the stop five below). JPEG's gamma curve spends more on shadows (~15 there), which is fine for viewing but not for editing. A Pocket 4 raw spans 0–62400 (≈ 975 steps even five stops down; one photo used 16,899 distinct values).
**Why it mattered:** float32 internally, 16-bit intermediates, and 8-bit only at final export (AGENTS.md). Every adjustment happens while there are still plenty of steps.

## 2026-10-12 · Why shoot RAW when the output is a JPEG
A camera JPEG is the camera running its *own* pipeline and discarding the inputs: white balance, highlight handling, tone curve, noise reduction and sharpening are baked into 8 bits. A RAW keeps those decisions open: WB is two numbers in metadata, highlights above display white survive (up to ~2 stops in our photos), and shadows have thousands of steps. picturesq applies the look in scene-linear float *before* the display transform and 8-bit export, so it works on the full data. For easy, well-exposed scenes the camera JPEG can be close; the gap shows up in hard scenes (sun in frame, night, mixed light) and in batch consistency, since normalise must measure each photo's real exposure rather than undo a per-frame auto-correction.
**Why it mattered:** this is the case for the whole tool, and why the M1 exit criterion compares our neutral render against the in-camera JPEG.

## 2026-10-12 · Licences: maths vs files, and "no licence"
Copyright protects *expression* (source code, a written config, a particular LUT file), not the idea or the maths behind it. So we may re-implement AgX from its published description, but not copy or line-by-line translate darktable's GPL code: the translation would be a derivative and would pull picturesq under the GPL. A repo with **no licence** is not free to use; the default is "all rights reserved", which rules out bundling Sobotka's or AgXc's files. Content under CC BY-SA (the RawTherapee film-simulation collection) can be used, but anything derived from it must stay CC BY-SA, so it lives outside our MIT tree as an optional download.
**Why it mattered:** ADR 0007: our AgX is written from the maths with our own tuned defaults in config, and no third-party colour files ship with picturesq.

## 2026-10-12 · The sRGB curve is not gamma 2.2
The sRGB **transfer function** has two pieces: below scene-linear 0.0031308 it is a straight line (×12.92), above it a 1/2.4 power with a small offset. In the midtones it looks like a 2.2 gamma (mid grey 0.18 encodes to 117.6/255 with sRGB vs 117.0 with 2.2), but near black they part ways: linear 0.001 encodes to 3.3/255 with sRGB and 11.0/255 with a pure 2.2 power. The straight segment exists because a pure power curve is infinitely steep at zero, which amplifies sensor noise and is hard to invert accurately. picturesq's curve also *extends* past 0–1 (negatives follow the line, values above 1 the power) so out-of-gamut and highlight values survive a round trip; clipping happens only at 8-bit export.
**Why it mattered:** `colour/transfer.py` implements the exact piecewise curve, tested against colour-science; using `x ** (1/2.2)` would have lifted every shadow in every export.

## 2026-10-12 · EV is log2 of light
One **stop** (1 EV) is a doubling of light, so the natural scale for exposure is `log2`: `EV = log2(value / 0.18)` measures brightness in stops relative to mid grey (0.36 is +1 EV, 0.09 is −1 EV). Adding EV is multiplying light, which is why exposure changes are `× 2**ev` in scene-linear and never additions to encoded values. Zero light is −∞ EV, so the conversion clamps tiny and negative values to a floor (2⁻²⁰, ≈ 17.5 stops below mid grey, far below any sensor's range).
**Why it mattered:** normalise (M2) computes `gain_ev = log2(target / median)`, and the AgX display transform (#17) works on a log2 encoding of the image; both use `linear_to_ev` / `ev_to_linear`.

## 2026-10-12 · A colour space is primaries + white point + transfer function
"RGB" alone means nothing: `[0, 1, 0]` is a different green in sRGB and in Rec.2020. A colour space pins down three things: the **primaries** (which exact red, green and blue the channels mean, as xy points on the CIE chromaticity diagram), the **white point** (the colour of R = G = B; both of ours use D65 daylight), and the **transfer function** (linear for our working space, the sRGB curve for JPEGs). Between two linear spaces, conversion is one 3×3 matrix, usually built via **XYZ**, the reference space all others are defined against: `RGB_a → XYZ → RGB_b`. Each RGB → XYZ matrix is derived from just the primaries and the white point. Matrices only work on linear values; applying one to sRGB-encoded numbers shifts colours.
**Why it mattered:** `colour/spaces.py` derives the Rec.2020 ↔ Rec.709 ↔ XYZ matrices from the primaries. Decode (#15) lands in Rec.2020; export (#18) converts to Rec.709 primaries and only then applies the sRGB curve. We derive rather than copy the rounded matrix printed in the sRGB standard, because that one maps white to `[0.99984, 1.00010, 1.00007]` (ADR-0008).

## 2026-10-12 · Gamut: why negative pixel values are normal
A **gamut** is the triangle of colours a set of primaries can mix. Rec.2020's triangle contains sRGB's, especially in greens and cyans, so some colours a camera records (foliage, neon, saturated flowers) exist in our working space but not in sRGB. Converting one doesn't fail: it produces a **negative channel**. Rec.2020 `[0.2, 0.6, 0.2]` becomes sRGB `[−0.035, 0.653, 0.160]`, where "negative red" means "greener than sRGB's green". Clipping negatives to zero shifts hue and flattens detail in saturated areas. Handling them gracefully is one of the display transform's jobs.
**Why it mattered:** the matrix and transfer functions keep negatives instead of clipping (they round-trip), the working space is Rec.2020 so grading never loses those colours, and AgX (#17) must compress out-of-gamut colours before the 8-bit export clips.

## 2026-10-14 · How AgX turns scene light into a picture
A display shows 0–1, but a scene spans 16+ stops, so something must decide where each stop lands. AgX does it in four steps. **Inset**: mix a little of each channel into the others (a matrix that pulls the primaries toward white). **Log encoding**: each channel becomes its EV relative to mid grey, scaled so `min_ev` (−10) is 0 and `max_ev` (+6.5) is 1, so every stop gets equal room. **Sigmoid**: an S-curve through mid grey: a straight middle (slope = `contrast`), a **toe** easing into black and a **shoulder** easing into white. **Outset**: give back some saturation. Because the curve runs per channel, a bright blue sky's channels all approach 1 as they climb the shoulder, so it fades to white with its hue intact (**path to white**). Without the inset, a pure primary has two channels near 0 that never rise, so it would stay saturated and clip with a hue shift. The hard clip we had before mapped everything above scene 1.0 (2.5 stops above mid grey) to white; AgX keeps detail up to +6.5 EV.
**Why it mattered:** this replaced the v0 hard clip (#17). At matched exposure (ADR 0009) the DJI sky kept its clouds instead of going white. Inset and outset were tuned by *measuring* Oklab hue drift on saturated exposure ramps (more inset = less drift but duller colour), not by eye.

## 2026-10-14 · Measure the camera before copying it
We assumed the camera JPEG was brighter because it "normalises" each photo (meters the scene and lifts dark ones). Measured on 24 photos, the brightening needed to match the camera was **+2.3 EV on almost every photo**, and the scene's own brightness predicted none of the variation. The camera isn't adapting per scene; its **tone curve** is simply brighter than ours: it puts our mid grey at 59 % display brightness (we put it at 18 %), has a steep middle and a strong shoulder. You can measure that curve without aligning images: sort each image's pixels by brightness (**quantile matching**) and pair them up, so the 30 % darkest of ours maps to the 30 % darkest of theirs. Fitting our exposure + AgX parameters to that curve got within 0.07 stops.
**Why it mattered:** normalise got a constant camera-fitted exposure offset instead of key detection and per-key targets, and the defaults have measured provenance. It also killed local tone mapping, which the plan thought the camera needed (ADR-0010).

## 2026-10-14 · Why per-channel curves wash out bright colours
AgX applies its S-curve to R, G and B separately. A bright sky blue might be R 0.4, G 0.6, B 1.2 in scene light: on the shoulder all three get squeezed toward 1, so their *ratios* shrink and the colour drifts toward white. That's the intended "path to white" for very bright lights, but cameras do much less of it: our brightest tones had a third of the camera's chroma. Tone-mapping **luminance only** and scaling R, G, B by the same factor keeps the ratios (and the saturation) but can push a channel past 1, so those pixels are pulled toward grey of the same luminance until they fit (**gamut fitting**). Blending 70 % of that with 30 % AgX keeps skies blue while extreme highlights still reach white.
**Why it mattered:** `chroma_preservation` and `saturation_fade` in the display transform; the boost fades toward white because boosting an already-bright colour only pushes its blue channel against 255.

## 2026-10-14 · Colour noise lives in the chroma channels
Sensor noise shows up as random brightness speckle (**luma noise**) and blotchy red/green/magenta speckle (**chroma noise**). Our eyes resolve colour much more coarsely than brightness, which is why JPEG stores colour at half resolution. So you can smooth only the colour heavily without the photo looking soft: each pixel keeps its own luminance and takes the local average **chromaticity** (its R, G, B divided by its luminance), only in the shadows, where noise is worst relative to signal. (We first did this in Oklab a/b; the linear version gives the same effect at about a third of the cost.) Blurring a small copy and upsampling it is far cheaper than a wide blur at full resolution, because the result is smooth anyway.
**Why it mattered:** `normalise.chroma_nr`; it took our darkest tones from 1.33× to ~1.06× the camera's chroma.

## 2026-10-16 · Base and detail: why one curve can't keep a sky's clouds
A display transform is one curve applied to every pixel. In its **shoulder** the curve is nearly flat: at 3.5 stops above mid grey ours climbs 0.19 display stops per scene stop, so a cloud 0.3 stops brighter than the sky around it ends up 0.06 stops brighter, which is invisible. Making the shoulder steeper would fix the clouds but blow out the whole sky. The way out is to treat *where* a tone is and *what's on top of it* separately. Split log brightness into a **base** (the blurred, broad brightness of each area) and **detail** (the difference). Run the base through the curve as before, so the sky as a whole still lands where the camera puts it, and give the detail its own, steeper slope (we keep at least 0.8). The blur must not cross big edges: averaging a bright sky with dark hills at the horizon would make the base wrong on both sides and leave a glowing band (**halo**). An **edge-aware** blur (the domain transform) treats a big brightness step like a wall.
**Why it mattered:** `grade.local_contrast` (ADR-0011) brought clouds and distant ridges back without moving the global brightness that the camera-matching work fitted. The first version used a guided filter and the tests caught a 1.5-stop halo above a synthetic horizon; sun glints taught us to amplify small detail only (`detail_limit_ev`).

## 2026-10-17 · Ringing: why a sharp resize turns sun glints black
Shrinking an image means averaging neighbouring pixels with a weighting **kernel**. A box kernel (plain area average) only ever adds positive amounts, so it can't overshoot, but it's slightly soft. Sharp kernels such as **Lanczos** have small *negative* lobes: next to an edge they subtract a little of the far side, which makes edges crisp and leaves a faint dark/bright fringe (**ringing**). On a JPEG that fringe is a few percent and invisible. In scene-linear light an edge can be a 100:1 jump: a sun glint at 40 next to water at 0.4. A few percent of 40 is more than the water's own value, so the pixels beside the glint go *below zero*, and the display transform shows them as black. The usual fix in video scalers is **anti-ringing**: clamp each sharp result to the range of the nearby source pixels. We take that range from a box-shrunk copy (3×3 neighbourhood), so ordinary edges keep Lanczos's sharpness and only the overshoot is cut.
**Why it mattered:** dark speckle inside sun glints (#55) came from the 2048 px web resize, not from highlight reconstruction or colour: R03 had 558 black pixels after Lanczos, none at full resolution and none with the clamp (`export/resize.py`).

## 2026-10-17 · A camera has two colour matrices, and the light decides the mix
A sensor's red, green and blue filters don't match human vision, so every RAW needs a 3×3 **colour matrix** to turn camera RGB into real colours (XYZ). One matrix can't be exact for every light: the error a 3×3 matrix makes depends on the spectrum lighting the scene. So a DNG stores two, each fitted under one **calibration illuminant**, usually tungsten (2850 K) and daylight (6500 K). The DNG specification says to blend them by the photo's white: find the white's **colour temperature** from the as-shot neutral, then weight the matrices linearly in 1/temperature. The temperature depends on which matrix you use, so it's solved as a small fixed-point problem. LibRaw skips all this and always uses the daylight matrix.
**Why it mattered:** with the specification's blend, skies came out 1.3° less purple and warm tones 2° truer; the tungsten-lit Pentax sample takes 74 % of the tungsten matrix instead of none (`decode/dng_colour.py`, ADR-0012). The DJI Pocket 4's two matrices are so different that the naive iteration flips between them forever, so we bisect on the weight.

## 2026-10-17 · Memory colours: cameras don't render skies accurately, on purpose
People remember some colours more vividly than they measure: blue sky, green grass, skin. Viewers prefer pictures closer to the remembered colour, so camera makers tune their JPEG engines toward it. Measured pixel by pixel against the DJI Pocket 4's JPEGs, an accurate render of a blue sky is about 1.4× less colourful, lighter, and ~4° more purple (in Oklab hue) than the camera's. The DJI's own colour profile in the DNG (`ProfileHueSatMap`) doesn't reproduce it, and the Fujifilm samples' JPEGs barely do it at all: it's a maker's choice, not physics. Reproducing it needs a targeted adjustment, not a different tone curve: a hue window around sky blue where hue turns toward cyan, chroma rises and lightness drops a little, fading to nothing for greys and other hues.
**Why it mattered:** `grade.display_transform.blue_rendering` (ADR-0012), on by default and fitted with leave-one-photo-out checks; a free-form per-hue table fitted the training photos but got *worse* on held-out ones (overfitting with only 13 photos), so we kept three amounts.

## 2026-10-17 · Bringing a colour into gamut without changing its hue
After a colour boost, some pixels need a channel above 1 or below 0, which the display can't show. The simple fix pulls the pixel in a straight line in linear RGB toward the grey of the same luminance until it fits. In linear light, mixing a blue with grey doesn't keep the hue we *see*: blues drift toward purple (the Abney effect). Oklab was designed so that its hue angle matches perceived hue, including for blues, so the better fix keeps Oklab lightness and hue and lowers only Oklab chroma until the colour fits, found by bisection. ACES 2.0 does the same in its own perceptual space.
**Why it mattered:** the blue rendering's boost uses this fit (`colour/oklab.py::fit_gamut_oklab`), so deep skies don't drift purple when they hit the edge of sRGB; a test shows the linear pull bending the same blues and the Oklab fit keeping them within 0.2°.

## 2026-10-17 · Compare like with like: a brightness error disguised as a colour error
To check our colour against the camera's, we averaged chroma in lightness bands: "how colourful are our near-whites compared with the camera's near-whites?" Each image was banded by its own lightness. But if our export is 0.75 stops darker, the camera's near-white band holds a sunlit wall while ours holds a few lamp highlights: we were comparing different things, and a pure brightness difference came out as a colour difference. This is **confounding**: a second variable (brightness) leaks into the one you meant to measure (colour). The fix is to compare at the same content: align the two images, take the bands from *one* image's lightness (the camera's, since it's the target) and read both images' chroma at those same pixels. Aligning needed more than a shift: cameras frame a little differently from the RAW (a 3:2 crop, in-camera distortion correction), so we also try small zooms and keep the one that lines up best (**phase correlation** finds the shift for each).
**Why it mattered:** the colour gate (`preview/compare.py`, ADR-0013). It confirmed that the remaining CC0 failure, Pentax near-whites, is a real white-balance difference (#57) and not a measurement artefact.

## 2026-10-17 · The sensor records more than the photo
A RAW file holds every pixel the sensor read, which is more than the photo. Around the edge are a few rows and columns the demosaic can't fill properly (they lack neighbours), and if the camera was set to a different aspect ratio than its sensor (3:2 or 16:9 on a 4:3 sensor), the whole sensor is still recorded and the framing is just a note in the file. The DNG calls that note the **default crop**; other makers have equivalents, which LibRaw reads for us. The camera's own JPEG always applies it; a RAW converter that doesn't shows strips the photographer never saw in the viewfinder.
**Why it mattered:** our Pentax Q7 exports were 4:3 while the photographer framed 3:2 (#61). `decode.default_crop` now applies it after LibRaw's demosaic (and after lens corrections, which are defined on the whole image). LibRaw also rotates its output for portrait photos, so the crop rectangle has to rotate with it; we pinned down LibRaw's rotation codes by forcing them on a sample rather than guessing.

## 2026-10-17 · EXIF: a typed little database inside every photo
EXIF is a small TIFF structure inside a JPEG's APP1 segment: directories (**IFDs**) of entries, each a tag number, a **type** and a value. IFD0 describes the image (make, model, orientation) and points to the EXIF IFD, which describes the capture (exposure time, f-number, ISO, lens). Values aren't floats: an exposure time is a **rational**, two 32-bit integers (1/250), and exposure compensation is a *signed* rational because it can be negative. Readers trust the type the specification gives each tag, so writing `0` as an unsigned rational is a validation error even though the number is right. Copying metadata from a RAW to an export isn't "copy everything" either: the RAW's orientation tag would rotate already-upright pixels a second time, its dimensions describe the sensor, MakerNote is a maker-private blob full of absolute file offsets that break when moved, and serial numbers and GPS are private.
**Why it mattered:** exports carry an allowlist of capture EXIF written with the specification's types (`export/exif.py`, ADR-0014); Pillow chose types from values, and ExifTool's validator caught it.

## 2026-10-17 · Proxies: half-size decoding and float16
Interactive work never needs 33 megapixels: a preview is at most a screen wide. A RAW has a cheap shortcut to a smaller image: each 2×2 block of the Bayer mosaic holds one red, two green and one blue sample, so treating the block as one pixel gives a full-colour image at half the width and height **without demosaicing**, the slowest step. It's a little softer and slightly differently aliased than a demosaiced-then-shrunk image, but the colours and brightness are the same (our test allows 0.05 stops per channel; the samples are well inside it). The result is stored as **float16**: 1 sign bit, 5 exponent bits and 10 mantissa bits, so about 3 significant digits from 0.00006 to 65504. That's coarse for maths but plenty for a scene-linear image that a preview will quantise to 8 bits, and it halves the cache. Values above 1 (highlight headroom) and negative out-of-gamut channels survive, which an 8- or 16-bit integer cache would clip.
**Why it mattered:** `pipeline/proxy.py` and `picturesq decode`. A Pocket 4 proxy builds in ~2 s instead of a ~5 s full decode, loads in ~0.3 s and takes 14 MB. The cache key covers everything that changes the pixels (original bytes, decode config, version), so a stale proxy can't be shown.

## 2026-10-17 · Where an export's memory and time go
A float32 RGB image costs 12 bytes per pixel, so one 33 MP Pocket 4 image is 380 MiB, and a numpy expression like `np.rint(np.clip(x, 0, 1) * 255)` allocates a new full-size array at every step. What matters for running several photos in parallel is the **peak resident memory** of a process (the most RAM it ever held), which the operating system tracks as the high-water mark (`ru_maxrss` on Linux). Time is a separate story: numpy's element-wise maths (`multiply`, `power`, `arctan2`, …) runs on **one core**, so an 8-core laptop is mostly idle. numpy releases Python's GIL while it computes, so threads over blocks of rows do run in parallel without multiplying memory, unlike one process per photo.
**Why it mattered:** measured, a Pocket 4 export peaks at 1.78 GiB (about four full-size images alive at once) and takes 63 s, 35 s of it the display transform at full resolution for the `archive` output. A 2.5 GB budget therefore fits one worker, not the 2–3 the plan guessed. `pipeline/budget.py` models the photo peak, and a slow test keeps it honest.

## 2026-10-17 · Cores, caches, hyperthreads and the GIL
A laptop's "8 CPUs" are often **4 physical cores with 2 hyperthreads each**. A hyperthread duplicates only the bookkeeping that tracks which instruction a thread is on; the arithmetic units and cache are shared with its sibling. That fills gaps when one thread is waiting on memory (web servers gain ~15-30 %), but numpy's tight loops keep the arithmetic busy and need the cache, so two threads per core only take turns and evict each other's data: on the i5-8250U, 8 threads were slower than 4. All cores also share **one connection to main memory**. Each numpy step (`multiply`, then `power`, then `add`) writes a temporary array; if a block's temporaries fit in the core's cache, they never touch main memory and cores scale; if not (our old 256k-pixel blocks), every core queues for the same memory and 4 threads gave only 1.5×. Python's **GIL** lets one thread run Python code at a time, but numpy releases it inside each operation; the few microseconds of Python per call still serialise, so tiny blocks (16k pixels) were *slower* on 4 threads than on 1. The sweet spot is in between: too small is GIL-bound, too big is memory-bound. Last gotcha: glibc gives every thread its own **memory pool (arena)** that keeps freed blocks instead of returning them, so a threaded export's peak rose by 0.5 GiB until we limited it to one shared pool.
**Why it mattered:** `picturesq.parallel` runs blocks of each image on one thread per physical core, with blocks sized from the CPU cache (`picturesq.hardware`); both are detected per machine. A 33 MP export went from 63 s to 28 s and from 1.78 to 1.18 GiB. The output is bit-identical for any thread count and block size (tested), which is what makes per-machine tuning safe for reproducibility.

## 2026-10-17 · Demosaicing: guessing two-thirds of every pixel
Each photosite under a Bayer mosaic measures one colour, so a demosaic has to estimate the other two from neighbours. The simplest way (`linear`, bilinear interpolation) averages the nearest photosites of the missing colour. In flat areas that's fine, but across an edge it averages both sides: a dark-to-bright step gets a soft, alternating **zipper** pattern, and fine stripes finer than the 2×2 pattern produce **false colour** (rainbow moiré on fabric or distant roof tiles), because red, green and blue were sampled at slightly different places. Better algorithms look for the edge first. **AHD** (adaptive homogeneity-directed), our default, interpolates each pixel twice, once horizontally and once vertically, and keeps whichever result is more uniform with its neighbourhood, so it interpolates *along* an edge, never across it. Fujifilm's X-Trans sensors use a 6×6 pattern instead of 2×2, and LibRaw always uses its own X-Trans demosaic for them. A demosaic is also the slowest part of decoding, which is why proxies skip it: each 2×2 block already has one red, two greens and one blue.
**Why it mattered:** `decode.demosaic` (default `ahd`) is passed to LibRaw in `decode/raw.py`; the setting is ignored for the two Fujifilm samples. The proxy path (`half_size=True`) has no demosaic at all, so previews can't show demosaic artefacts that exports would have, or the other way round; the proxy test checks only that colour and brightness agree.

## 2026-10-17 · Why clipping turns bright blues cyan and oranges yellow
Clipping a scene-linear image to the display's 0–1 range works per channel, and a colour's channels reach 1 at different exposures. A sky blue of R 0.06, G 0.17, B 0.42 (scene-linear Rec.709) hits B = 1 about 1.3 stops brighter. From there blue stays at 1 while green keeps rising, so the ratio between them, which *is* the hue, changes: the blue turns **cyan**, then white once green and red catch up. An orange (R 0.50, G 0.14, B 0.03) clips red first and slides toward **yellow**. The same happens to any per-channel curve whose top is flat, only more gradually. A display transform avoids it by making the channels converge *together*: AgX mixes a little of every channel into the others before its curve (the inset), so as a colour brightens all three channels climb the shoulder in step and it fades toward white along its own hue (the **path to white**).
**Why it mattered:** this is the visible case for the display transform over "sRGB curve and clip" (ADR-0003), shown as exposure ramps in the [M1 primer](primers/m1-neutral-render.md) (`scripts/primer_figures.py`). It's also why the clip happens only once, at 8-bit export, after AgX has already brought every value inside 0–1.

## 2026-10-18 · Amdahl's law: why a second photo helps and a fourth doesn't
If a fraction of a job can't be split across cores, it limits the speed-up however many cores you add. That is **Amdahl's law**: with a serial fraction *s*, *n* cores give at most 1 / (s + (1 − s)/n). Within one photo, some parts are serial: LibRaw's decode, Pillow's JPEG encoding, the Python between numpy calls. Measured, 4 threads made an export ~2.2× faster, not 4×, which is about what a third of the time being serial predicts. Exporting a second photo at the same time fills those serial gaps, because the two photos don't wait on each other. More photos stop helping once the cores are busy, and they compete for the one connection to main memory and the shared cache. Every photo in flight also holds its own full-resolution arrays, so memory, not cores, usually sets the limit.
**Why it mattered:** on the 4-core laptop, 2 photos × 2 threads exported a batch 5-17 % faster than 1 × 4, and 4 × 1 was no faster than 2 × 2 with ~50 % more memory (ADR-0015). So `picturesq.pipeline.workers` runs photos side by side only while their predicted photo peaks fit the memory budget, at most cores ÷ 2 at a time, and gives each photo the cores ÷ photos running when it starts.

## 2026-10-18 · Temperature, tint and mired: two numbers for a white
Heat a black body and it glows red, then orange, white and blue; the chromaticities it passes through form a curve called the **Planckian locus**. A light's **colour temperature** is the point on that curve nearest to it. Most real lights (daylight, fluorescent tubes, LEDs) aren't exactly on the curve, so a second number says how far off it they are: **Duv**, the signed distance from the locus in the CIE 1960 uv diagram (positive above it, greener; D65 is about +0.003). "Nearest" is measured along **isotemperature lines**: short lines crossing the locus at right angles in uv, every point on which has the same correlated temperature. Robertson (1968) tabulated 31 of them and interpolates between them, which is what the DNG SDK and colour-science use. Photographers know these two numbers as Lightroom's **temperature** and **tint** sliders; we define `tint = -1000 × Duv`, so positive is magenta like Lightroom; Adobe's DNG SDK scales tint about three times larger (-3000 × Duv), so the numbers differ. Kelvin is a misleading ruler, though: our eyes respond roughly to its reciprocal, so 2000 → 2500 K is a big visible shift while 10000 → 10500 K is barely visible. **Mired** (`1e6 / kelvin`) fixes that: 2000 → 2500 K is 100 mired, 10000 → 10500 K under 5, and equal mired steps look about equally different. Robertson's table is spaced in mired for the same reason.
**Why it mattered:** `colour/temperature.py` now converts kelvin and tint to xy and back (`kelvin_tint_to_xy`, `xy_to_kelvin_tint`, round-trip within 1 K and 0.1 tint), and `white_balance_matrix` re-balances a linear Rec.2020 image from one white to another with Bradford. The WB check (#83) compares the as-shot white with our estimate in mired, and kelvin overrides (#87) turn a user's temperature and tint into that matrix.

## 2026-10-18 · Histograms and percentiles in EV; why the median and not the mean
A photo's brightness isn't one number, it's a distribution: its **histogram** counts how many pixels sit at each level. In scene-linear, that histogram is useless to read, because every stop doubles the value: a 10-stop scene puts its shadows in the first 0.1 % of the axis. Measured in **EV** (`log2(value / 0.18)`, so mid grey is 0 and each stop is 1) the same scene spreads evenly, and "the shadows are 3 stops under mid grey" becomes a plain number. A **percentile** summarises the distribution without drawing it: p5 = −3 EV means 5 % of the pixels are darker than 3 stops below mid grey; p50 is the **median**, p1 and p99 the darkest and brightest ends, ignoring the most extreme 1 % (a few dead or specular pixels shouldn't define a photo). `p99 − p1` is how many stops the photo spans. Because `log2` keeps values in the same order, the percentile of the EVs is the EV of the percentile, and doubling the light moves every percentile by exactly +1 EV. Why the median rather than the mean: the mean of linear values is dragged by the brightest few pixels. A grey street (0.1) with the sun in 1 % of the frame (at 1000) has a mean of 10.1, about 6 stops above what you see almost everywhere; its median is still 0.1. The mean of EVs has the opposite bias toward deep shadows and can't handle zero-valued pixels. The median says "half the photo is brighter than this", whatever the extremes do.
**Why it mattered:** `normalise/stats.py::photo_stats` stores p1/p5/p50/p95/p99 in EV, the dynamic range, the clipped fraction and the mean Oklab chroma for each photo, on the same ~100k-pixel grid as `median_ev`, so its p50 is exactly the median that exposure correction uses. Outlier flags (#84) and `picturesq normalise` (#85) read them.

## 2026-10-18 · Grey-world: the average colour is not always grey
The simplest way to estimate the colour of the light from a photo is **grey-world**: assume the scene, averaged over every pixel, is grey, so whatever colour the average has must come from the light. It works for varied scenes (a street, a landscape with sky and ground) and fails whenever one colour fills the frame: a wooden table, a beach, a forest, a sunset. Grey-world then mistakes a warm scene for warm light and neutralises the scene itself. Restricting the average to well-exposed, low-chroma pixels (likely neutral surfaces) helps, but no estimate from pixels alone is always right, because a white card under orange light and an orange card under white light can produce the same numbers.
**Why it mattered:** on the tungsten-lit Pentax K-5 II s sample, plain grey-world estimates 2686 K against the camera's recorded 3332 K (72 mired apart), turning the table grey and the white card blue ([M2 primer](primers/m2-normalise.md)). So normalise's white balance check (#83) only **flags** disagreement (`wb_disagreement`), and the user decides, with `wb_kelvin`/`tint` overrides if needed.

## 2026-10-18 · Judge noise at the size people will see
Noise is random, so averaging neighbouring pixels partly cancels it: the average of *n* independent noisy values has 1/√*n* of the noise. Shrinking a photo averages pixels, so a 4240 px wide photo shown 1080 px wide (about 15 pixels into each) has roughly a quarter of the noise it shows at 100 %. Detail is not random and survives the averaging much better. That's also why luma (brightness) noise reduction is hard: noise and fine detail are both small, high-contrast variations, and a filter that removes one softens the other, while colour noise can be smoothed freely because our eyes resolve colour coarsely.
**Why it mattered:** picturesq does chroma NR only (`normalise.chroma_nr`) and defers luma NR until night photos at output size show they need it (project plan §11). The [M2 primer](primers/m2-normalise.md) shows an ISO 20000 crop at 100 % next to the whole photo at output size, where the same noise has nearly vanished.

## 2026-10-18 · As-shot white balance, and why "clipped" isn't 1.0
A camera doesn't record the colour of the light directly. It records the **white balance** it chose: three per-channel gains that would make a neutral surface come out with equal red, green and blue. A DNG stores their inverse, `AsShotNeutral`: the camera RGB a grey card had, e.g. (0.64, 1, 0.37) for the Pentax K-5 IIs interior, lots of red and little blue, i.e. warm light. Pushed back through the camera's colour matrix that neutral becomes an xy chromaticity, which we describe as a colour temperature (3330 K, tungsten-ish) and a **tint** (how far off the black-body line, green or magenta). The clip level is the other half of what the header tells us. LibRaw scales each raw channel by its white-balance gain *and* normalises the gains, by their smallest with `highlight_mode: clip` (so every channel reaches the top and a clipped white is exactly white) but by their largest otherwise (so the strongest channel reaches the top and the others stop short, which is what gives the highlight modes something to blend or reconstruct). With `blend`, our default, a fully clipped white comes out neutral at the mean gain over the largest: 0.82 for the Fujifilm XQ1, not 1.0. The DNG baseline exposure then multiplies it (the K-5 IIs's 0.49 EV turns 0.65 into 0.91).
**Why it mattered:** `decode/info.py` reads both from the header so the normalise stage can count blown highlights at the right value (#81) and compare the camera's white balance with the scene's (#83). Counting pixels at 1.0 would have found none in a `blend` decode of a blown-out sky.

## 2026-10-18 · Reading a camera's white balance off its own JPEG
A camera records the white balance it used (`AsShotNeutral` in a DNG), but its JPEG engine could still neutralise more or less than that, so "the camera's white" and "the recorded white" might differ. You can measure what the JPEG did: line our render up with it pixel for pixel, pick the pixels the camera rendered grey, and ask which white, adapted to D65 with Bradford, would turn our colour at those pixels into the camera's. That white, in mired against the recorded one, is the camera's extra adaptation. Measured on 15 photos it was within 15 mired every time, so the recorded white *is* what the JPEG uses; the cream Pentax card under tungsten was the one case leaning the other way, by 15 mired.
**Why it mattered:** it decided ADR-0016: normalise keeps the as-shot white balance and only flags photos (`wb_disagreement`, opt-in since it fired on genuinely coloured scenes) where two estimates of the light agree it looks wrong. A correction toward an estimate would have moved photos away from the camera more often than toward it.

## 2026-10-18 · Even isn't the same as right
Pulling every photo's median brightness to the same value makes a batch look even, but a photo's median is part of what it means. A sunset or a club is **low-key**: mostly dark, with a few bright lights, and it's meant to look dark. A snowy or overcast beach is **high-key**: mostly bright. Matching the medians brightens the first and darkens the second until both look like a grey afternoon, which throws away the mood the photographer saw. It also moves the ordinary photos: on the reference set, daylight photos sit around +1.3 to +2.3 EV at the default, so pulling every median to +1 EV made most of them darker.
**Why it mattered:** `normalise.exposure.correction` stays off by default. picturesq flags outliers and too-dark photos instead of forcing them, and the fix is per photo (`photos.<name>.normalise.exposure_ev`, `wb_kelvin`, `tint`), with sliders in the UI's per-photo normalisation review (M4).

## 2026-10-18 · Why a ratio of two near-zero numbers is a bad test
A ratio says how many times bigger one number is than another, which is the right question when both are clearly above zero: a sky with 1.3× the camera's chroma looks visibly more saturated. Near zero it stops meaning anything. A near-white wall is almost colourless in both images; if the camera's chroma there is 0.006 and ours 0.016, that is 2.7× "too colourful", yet both are below the ~0.02 Oklab chroma where the eye notices a tint, and a rounding step or a little noise can swing the ratio by 50 %. The same holds for any relative error (percentage error of a tiny value, signal-to-noise near the noise floor): the denominator, not the difference, drives the result. The usual fix is a combined test, as in `numpy.isclose`: pass when the *relative* difference is small **or** the *absolute* difference is small, each covering the range where the other is meaningless.
**Why it mattered:** the colour gate failed the CC0 samples on the near-white band only because of this, while the user saw nothing wrong side by side. The band now also passes when ours and the camera's mean chroma differ by at most `CHROMA_ABS_TOLERANCE` (0.015) (`picturesq.preview.compare`, ADR-0013 amendment); coloured bands are still judged by the ratio.

## 2026-10-18 · Illuminant estimation, and why one estimator isn't enough
A photo records light reflected off surfaces, so its colours mix two unknowns: what colour each surface is, and what colour the light is. Working out the light from the pixels alone (**illuminant estimation**, the problem behind every camera's auto white balance) is therefore guesswork: every method assumes something about the scene. **Grey world** assumes the scene averages to grey, so the average colour is the light's; a forest averages green and gets "corrected" towards magenta. Restricting the average to nearly neutral pixels (low **saturation**, Oklab chroma ÷ lightness, so dark pixels aren't counted as neutral just because they're dark) and iterating removes most of that, but a scene full of sand or skin still fools it. **Brightest** (white patch) assumes the brightest unclipped surfaces are white or specular highlights, which reflect the light's colour; a sunlit yellow wall fools it. Clipped pixels have to be skipped: once a channel hits the clip level the pixel's hue is gone. Measured on the samples and the reference set, where the camera's as-shot white was right on every photo (its JPEG agreed within 15 mired), each estimator alone was 30 mired or more off on some photos, but rarely both on the same photo in the same direction, because they fail on different scenes. Requiring two independent guesses to agree is the same trick as a second opinion: it trades a little sensitivity for far fewer false alarms.
**Why it mattered:** `normalise/white_balance_check.py` runs both estimators on the decoded image, maps each estimate back to the scene by undoing the decode's Bradford adaptation (D65 → as-shot white), and raises `wb_disagreement` only when both are at least `flag_disagreement_mired` (30) from as-shot the same way. Of the six CC0 samples that flags only the Sony FX3 (both about 88 mired warmer); the Pentax tungsten interior (28 and 33) comes close. It never changes the photo (plan D6). Later (2026-10-18) the flag became opt-in (`flag_disagreement`, off by default): on the reference set it fired on 3 of 17 photos, all genuinely coloured scenes where as-shot was right, so the check's numbers stay in the stats but nobody is alarmed by default.

## 2026-10-18 · Why cameras add contrast to flat scenes, and why the pivot is high
A display transform maps scene EV to screen brightness with one fixed S-curve, built so that a typical scene spanning 8–10 stops fits between black and white. A flat scene (overcast light, fog, snow) spans only 2–3 stops between its 5th and 95th percentiles, so through that curve it fills a narrow band of the screen and looks grey and dull. A camera JPEG engine doesn't use one fixed curve: it measures the scene and makes the curve steeper when there is little range to show, like a photographer printing a dull negative on harder paper. On the two flat reference-set photos the camera's tones were 1.4–1.5× steeper than ours. Steeper around which point matters: around the median, half the tones would get brighter and the bright end (the sky, a snowfield) would move towards white and clip. The camera instead kept the bright end where it was and pushed everything darker down, as if the pivot were near the 75th–90th percentile. **Scene contrast** copies that: it works in scene-linear EV, is zero at the p75 pivot, moves darker tones down and brighter ones a little up, and uses `tanh` to level off far from the pivot (at most 0.75 stops with the defaults) so deep shadows aren't crushed. Every channel gets the same multiplier, so colours keep their hue and saturation, and greys stay grey. Changing every channel separately with a curve would shift colours instead.
**Why it mattered:** `normalise/scene_contrast.py` measures each photo's range and p75 on the exposure's sample grid and applies the gain a block of rows at a time, after chroma NR. Scenes 4.5 stops or wider are untouched, so it can't harm the usual photo. It's off by default (ADR-0017) because the evidence is two photos from one camera; the default amount is half of what matched the camera, which was the version the user preferred.

## 2026-10-18 · Intensity: scale the recipe, not the result
A look's intensity could work like a layer's opacity: render the look, then mix it with the untouched photo. That breaks for most operations, because mixing two images isn't the same as a weaker version of the change between them. A +1 EV look blended 50/50 with the original gives `(2x + x) / 2 = 1.5x`, which is +0.58 EV, not +0.5 EV, and blending at a hard edge shows two images on top of each other instead of one gentler one. Two white balances blended don't give a white balance in between, and a blend of a grey and a saturated version of a pixel drifts in hue unless the mixing happens in a perceptual space. The fix is to scale the *recipe*: each operation declares, for every value that sets how strong it is, the **neutral value** at which it does nothing (0 EV, 0 mired, contrast 0), and intensity moves that value from neutral toward the look's (`neutral + intensity × (value − neutral)`). The same reasoning puts contrast in log space: "20 % more contrast" means every stop away from mid grey becomes 1.2 stops, the same in the shadows and the highlights, which is how we see brightness.
**Why it mattered:** `picturesq.config.operations` marks each such value with `scaled(neutral)`, and `apply_operation` skips an operation that is neutral after scaling, so intensity 0 % is bit-identical to the neutral render (ADR-0019). Only `lut`, which has no strength value to scale, blends its output with its input.

## 2026-10-18 · Why colour operations work in OkLCh, not HSL
Photo editors' "HSL" sounds like the obvious space for hue and saturation tools, but HSL is just a re-arrangement of sRGB-encoded numbers: its "lightness" is `(max + min) / 2`, which has nothing to do with how bright a colour looks. Pure sRGB blue `(0, 0, 1)` has HSL lightness 0.5; desaturate it fully in HSL and you get the grey `(0.5, 0.5, 0.5)`, 0.21 in linear light. A grey that looks as light as that blue (the same Oklab lightness, 0.45) is 0.09: removing the colour made it **1.2 stops brighter**. **OkLCh** is Oklab in polar form: L (perceived lightness), C (chroma, the distance from grey) and h (hue, the angle). Because Oklab was fitted to how people judge colour differences, changing C or h at fixed L keeps the perceived brightness, and a hue shift of 10° looks about as big for a red as for a blue. That's what you want from "less colour" or "turn the greens a little yellower": only the thing you asked for changes. Hue tools also have to fade out near grey: a grey's hue angle is noise (its a/b are almost 0), so a pixel's band change is scaled by how colourful it is (`HSL_FULL_CHROMA`), otherwise sensor noise in a grey wall would be pushed in random directions.
**Why it mattered:** `saturation`, `vibrance`, `hsl` and `split_tone` (`picturesq.grade.operations`) all convert a block of pixels to Oklab, change a/b (and, for `hsl`, brightness in EV by an explicit gain), and convert back, so their lightness is kept to 1e-4 in tests. The hue band centres were measured in Oklab from sRGB colours (skin falls in `orange`, sky in `blue`), not copied from HSL's 0/60/120°.

## 2026-10-18 · What a 3D LUT is, and why tetrahedral interpolation
A 3D LUT is a colour-to-colour lookup table: a cube of N×N×N input colours (N is usually 17, 33 or 65) and, for each, the colour it should become. It can encode any colour change, however tangled (film emulations, a colourist's grade), which is why LUTs give looks breadth no list of simple operations can. Two things make one go wrong. First, the **input space**: the table's corners mean "this sRGB value", so feeding it linear values or a different curve lands every pixel on the wrong cell; the operation has to encode into the LUT's space and decode back. Second, **interpolation**: almost every pixel falls between grid points. Trilinear interpolation blends all eight corners of the surrounding cell; tetrahedral splits the cell into six tetrahedra that all share the grey diagonal (black corner to white corner) and blends only the four corners of the one the pixel falls in. For a grey pixel that tetrahedron's corners lie on the diagonal, so if the LUT keeps greys grey, interpolation keeps them grey too. In a test cell with the grey diagonal neutral but one coloured off-diagonal corner, mid grey through trilinear came out `(0.5, 0.5, 0.54)`, a blue cast, and through tetrahedral exactly `(0.5, 0.5, 0.5)`. It is also cheaper (four lookups, not eight), which is why Resolve and OpenColorIO default to it.
**Why it mattered:** `picturesq.colour.lut.apply_lut_3d` sorts each pixel's three fractions within its cell, which picks the tetrahedron, and sums four corners, all six cases in one numpy formula. It is checked against colour-science's tetrahedral interpolator (within 1e-5) and kept out of the runtime dependencies (plan D8).
